# Mapa de contratos, consumidores e cobertura — Sprint 4

## Objetivo e regra de leitura

Este documento responde, para cada contrato: qual regra ele declara, qual módulo realmente a consome, qual teste demonstra o comportamento e qual ação falta. Uma menção do arquivo em README, ADR, comentário ou teste de formato **não** é considerada consumo executável.

As referências de arquivos apontam para a linha integrada do repositório (`main`). As referências `#NNN` são [issues do GitLab](https://git.inteli.edu.br/graduacao/2026-2a/t13/g02/-/issues).

### Legenda do veredito

| Veredito | Significado | Tratamento |
| --- | --- | --- |
| **Coberto** | Regra é lida/aplicada no caminho relevante e há teste executável associado. | Preservar evidência e revalidar na regressão #160. |
| **Parcialmente coberto** | Parte da regra é aplicada ou testada, mas campos/aceites do YAML não são verificados. | Completar no #156 e criar regressões no #157. |
| **Não coberto — implementar** | Não há consumidor executável para uma regra que deveria valer no runtime canônico. | Implementar e testar no #156/#157. |
| **Dependência futura** | Requer trusted, DW ou report que ainda será materializado em outro card. | Não simular cobertura; vincular ao card bloqueador. |
| **Decisão externa/proposta** | Depende de aprovação do Data Owner ou política operacional ainda não homologada. | Registrar limitação, responsável e evidência requerida. |
| **Sem consumidor canônico** | O YAML descreve uma rota paralela/histórica sem leitor YAML no runtime integrado. | Decidir se a rota será canônica, integrada ou tratada como legada. |

## Resumo executivo

Existem **10 contratos YAML**. Três são carregados programaticamente por uma implementação de ingestão (`fontes_raw`, `staging`, `ingestao_raw_objectstore`); dois são parcialmente materializados no ETL orientado a portas (`fontes_raw` e `staging`); os contratos de trusted, DW, dashboard e retenção ainda não têm consumidor executável completo. Os contratos de ingestão por eventos e raw replicada possuem módulos e testes próprios, mas esses módulos repetem suas regras em Python/SQL e **não leem o YAML correspondente**.

Consequentemente, o #155 não deve concluir que todos os contratos são automaticamente aplicados. O principal encaminhamento é reduzir a divergência entre contrato, código e teste, sem forçar automação onde a regra depende de decisão de negócio.

| Veredito agregado | Contratos |
| --- | --- |
| Coberto de forma suficiente para o caminho atual | nenhum contrato inteiro; a cobertura é por regra e caminho. |
| Parcialmente coberto | `contrato_fontes_raw`, `contrato_staging`, `contrato_execucao_linhagem`, `contrato_ingestao_raw_objectstore`. |
| Não coberto no runtime canônico / dependência futura | `contrato_pesquisas_trusted`, `contrato_dw_analytics`, `contrato_dashboard_publicacao`. |
| Decisão externa/proposta | `contrato_retencao_arquivamento`. |
| Sem leitor YAML canônico | `contrato_ingestao_raw_replicada`, `contrato_ingestao_eventos_clickhouse`. |
